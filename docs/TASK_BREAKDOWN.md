## 0. 이 문서의 목적

[TECH_SPEC.md](./TECH_SPEC.md)에 정의된 구현 내용을 **작은 작업 모듈 단위**로 쪼갠 뒤, 순서대로 하나씩 구현·검증한다.

이렇게 나누는 이유:

1. **오류 감소**: 한 번에 큰 작업을 뭉쳐서 구현하면 문제가 어디서 생겼는지 추적하기 어렵다. 작은 단위로 나누면 각 단계마다 "제대로 동작하는 상태"를 확인하고 넘어갈 수 있다.
2. **LLM 세션(대화창) 제약 대응**: 하나의 대화 세션에 너무 많은 작업을 몰아넣으면 컨텍스트가 길어져 성능이 떨어지거나 오류 가능성이 높아진다. 모듈 단위로 **새 세션**에서 작업하고, 필요한 정보는 파일로 남겨 다음 세션에 전달한다.
3. **선행 의존성이 없어도 검증 가능**: 각 모듈은 뒤에 나올 다른 모듈이 아직 없다는 가정하에, 필요하면 목업 데이터/임시 구현으로 대체해서라도 그 자리에서 "구현 후 즉시 테스트"가 가능해야 한다.

## 1. 작업 원칙

- **모듈 하나 = 새 세션 하나**가 기본 원칙이다. 모듈이 너무 작아서 여러 개를 한 세션에 이어서 해도 컨텍스트에 무리가 없다고 판단되면 묶어도 되지만, 반대로 한 모듈이 커 보이면 더 잘게 쪼갠다.
- 모든 모듈은 **독립적으로 구현 + 테스트가 가능**해야 한다. 아직 구현되지 않은 선행 요소(백엔드 API, 인증 등)가 필요하면 목업 데이터나 임시 스텁으로 대체해서 검증한다. (예: 백엔드 없이 프론트를 만들었다면 목업 JSON으로 화면 동작을 확인한다.)
- 프론트엔드/백엔드로 통짜로 나누는 것이 목적이 아니다. **기능 단위(예: "회원 목록 조회", "출석 체크인 로직")**로 쪼개는 것이 원칙이며, 하나의 기능 안에서 화면과 데이터 처리를 함께 구현해도 된다.
- 각 모듈을 마치면 **핸드오프 요약 파일**을 작성한다 (2절 참고). 다음 세션은 이 파일 + PRD.md + TECH_SPEC.md를 읽고 시작한다.
- 모듈 순서는 의존관계를 따른다 (예: DB 스키마가 없으면 회원 CRUD를 실제로 연결할 수 없다). 단, 각 모듈 내에서는 목업으로 먼저 검증하므로 엄격하게 막히지는 않는다.

## 2. 세션 간 컨텍스트 인계 절차

### 2.1 핸드오프 파일

- 위치: `docs/handoff/HANDOFF_XX_모듈명.md` (XX는 모듈 번호 두 자리, 예: `HANDOFF_02_supabase-auth-setup.md`)
- 모듈 작업을 마친 세션의 **마지막 단계**로 아래 항목을 채워 저장한다.

```markdown
# Handoff: Module XX - <모듈명>

## 완료 상태
- [x] 구현 완료 / [ ] 부분 완료 (남은 부분: ...)

## 무엇을 했는가
- 생성/수정한 파일 목록과 각 역할 (경로 + 한 줄 설명)
- 주요 구현 결정 사항 (TECH_SPEC.md와 다르게 구현한 부분이 있다면 이유와 함께 명시)

## 테스트 결과
- 어떤 방법으로 검증했는지 (예: 목업 데이터로 화면 확인 / 실제 Supabase 연결 후 CRUD 확인)
- 확인된 항목 / 확인하지 못한 항목

## 다음 모듈 시작 시 필요한 정보
- 다음 모듈이 이어받아야 할 상태 (예: "members 테이블 스키마 확정됨, 컬럼은 TECH_SPEC.md 4.2절과 동일")
- 환경변수/설정 중 새로 생긴 것이 있다면 "어디에 있는지"만 기록 (실제 비밀값은 기록하지 않는다)
- 알려진 이슈/TODO

## 다음 모듈
- Module (XX+1) - <모듈명>: <TASK_BREAKDOWN.md의 해당 섹션 링크>
```

### 2.2 새 세션 시작 템플릿

새 대화창을 열 때 아래 형식으로 시작한다.

```
docs/PRD.md, docs/TECH_SPEC.md, docs/TASK_BREAKDOWN.md 의 Module <번호>,
그리고 docs/handoff/HANDOFF_<이전 번호>_*.md 를 읽고 이어서 작업해줘.
이번 세션 목표는 Module <번호>: <모듈명> 구현 및 테스트야.
```

- 첫 모듈(Module 0)은 이전 핸드오프 파일이 없으므로 PRD/TECH_SPEC/TASK_BREAKDOWN만 참조한다.
- 세션 종료 전에는 항상 "이번 모듈 핸드오프 파일 작성해줘"로 마무리한다.

## 4. 모듈 상세

### Module 0 — 프로젝트 초기 셋업

- **목표**: Next.js(App Router, TypeScript, Tailwind) 프로젝트를 생성하고 GitHub 저장소 + Vercel 배포까지 연결한다.
- **참고**: TECH_SPEC.md 2절(기술 스택), 6절(폴더 구조), 7절(배포/CI-CD)
- **산출물**:
  - Next.js 프로젝트 골격 (TECH_SPEC.md 6절 폴더 구조 기준 초기 디렉터리만 생성)
  - GitHub 저장소, `main` 브랜치
  - Vercel 프로젝트 연동 (아직 Supabase 환경변수는 없어도 됨)
- **테스트 방법**: 로컬 `npm run dev`로 기본 페이지 확인 → GitHub push → Vercel 자동 배포 URL 접속 확인.
- **이번 모듈에서 하지 않는 것**: Supabase 연동, 실제 화면/기능 구현.

### Module 1 — Supabase 프로젝트 & DB 스키마

- **목표**: Supabase 프로젝트를 생성하고 TECH_SPEC.md 4절의 테이블(members, memberships, attendances)을 만든 뒤 RLS를 켠다.
- **참고**: TECH_SPEC.md 4절(DB 설계), 8.5절(RLS 재점검)
- **산출물**:
  - Supabase 프로젝트
  - `supabase/migrations/`에 스키마 SQL 파일
  - 각 테이블 RLS 정책 (로그인 사용자만 CRUD)
- **테스트 방법**: Supabase SQL 편집기 또는 테이블 편집기에서 더미 데이터 insert/select/update/delete를 **로그인 세션이 있다고 가정한 API 키(익명 키+RLS 우회 없이)** 로 시도해 정책이 의도대로 동작하는지 확인. Advisor 실행해서 경고 없는지 확인.
- **이번 모듈에서 하지 않는 것**: Next.js 코드에서의 실제 연동.

### Module 2 — Next.js ↔ Supabase 연동 & 인증 가드

- **목표**: `@supabase/ssr`로 클라이언트/서버용 Supabase 클라이언트를 만들고, 로그인하지 않은 사용자의 접근을 막는 `middleware.ts`를 구현한다.
- **참고**: TECH_SPEC.md 3절(인증 설계), 6절(폴더 구조 중 `lib/supabase/`, `middleware.ts`)
- **산출물**: `lib/supabase/client.ts`, `lib/supabase/server.ts`, `middleware.ts`
- **테스트 방법**: 아직 로그인 화면이 없으므로, Supabase 대시보드에서 테스트 계정을 하나 만들어 임시 로그인 API 호출(또는 Supabase의 테스트용 매직 링크)로 세션을 발급받아 보호된 경로 접근 성공/실패 케이스를 각각 확인한다.
- **이번 모듈에서 하지 않는 것**: 회원가입/로그인 UI (Module 3에서 진행).

### Module 3 — 회원가입/로그인 화면

- **목표**: `/signup`, `/login` 페이지를 만들어 Supabase Auth와 연결한다.
- **참고**: TECH_SPEC.md 3.2절(인증 흐름), PRD.md 6절(화면 정의 중 로그인/회원가입)
- **산출물**: `/signup`, `/login` 페이지, 로그아웃 버튼
- **테스트 방법**: 실제 이메일로 가입 → (이 시점엔 이메일 확인이 꺼져 있어도 무방, Module 8에서 켬) → 로그인 → 보호된 페이지 진입 → 로그아웃 → 재접근 차단까지 E2E로 확인.
- **이번 모듈에서 하지 않는 것**: 이메일 확인/커스텀 SMTP/비밀번호 정책 강화(Module 8에서 진행).

### Module 4 — 회원 목록/등록/상세/수정 (회원 CRUD)

- **목표**: 회원 정보를 등록/조회/검색/수정할 수 있는 화면과 데이터 처리 로직을 구현한다.
- **참고**: TECH_SPEC.md 4.2절(members 테이블), PRD.md 6절(회원 목록/등록/수정/상세 화면)
- **산출물**: `/members`, `/members/new`, `/members/[id]` 페이지 및 관련 Server Actions
- **테스트 방법**:
  1. 먼저 목업 데이터(하드코딩된 배열)로 화면 레이아웃/검색/폼 동작을 확인한다.
  2. Module 1~2가 준비되어 있다면 실제 Supabase 연결로 교체해 등록 → 목록 반영 → 수정 반영 → 검색까지 확인한다.
- **분리 팁**: 화면이 크면 "목록+검색"과 "등록/수정 폼"을 별도 모듈(4-A, 4-B)로 더 쪼개도 된다.

### Module 5 — 회원권 등록 및 상태 계산

- **목표**: 회원 상세 화면에서 회원권(기간제/횟수제)을 등록하고, 상태(정상/만료임박/만료)를 계산해 표시한다.
- **참고**: TECH_SPEC.md 4.2절(memberships), 5.2절(회원권 상태 판정 로직)
- **산출물**: 회원권 등록 폼, 상태 계산 함수(순수 함수로 분리해 테스트 용이하게), 상태 뱃지 UI
- **테스트 방법**: 상태 계산 함수는 **단위 테스트**로 경계값(만료 정확히 7일 전, 당일, 하루 지남 / 잔여 횟수 2, 1, 0)을 검증한다. 화면은 목업 날짜로 각 상태가 올바른 색상/문구로 보이는지 확인한다.

### Module 6 — 출석 체크 & 횟수 차감

- **목표**: 회원 검색 → 체크인 → (횟수제인 경우) 잔여 횟수 자동 차감, 당일 중복 체크인 방지 로직을 구현한다.
- **참고**: TECH_SPEC.md 5.1절(출석 체크 & 횟수 차감 로직)
- **산출물**: `/attendance` 페이지, 체크인 처리 로직(원자적 차감을 위한 Postgres 함수 또는 트랜잭션)
- **테스트 방법**:
  1. 목업 회원/회원권 데이터로 체크인 UI 흐름 확인.
  2. 실제 DB 연결 후: 같은 회원을 하루에 두 번 체크인 시도 → 두 번째는 경고 처리되는지 확인.
- **⚠️ 요금제 확정에 따른 변경 (Module 5에서 반영)**: 현재 운영 요금제 4종은 모두 기간제라 **횟수 차감은 해당 없음**. 대신 **주간 횟수 초과 경고**를 구현한다 — 이번 주(월~일) 출석 수가 회원권의 `sessions_per_week` 이상이면 경고를 표시하되 **체크인은 허용**한다(사용자 확정 정책). 자세한 내용: [HANDOFF_05](./handoff/HANDOFF_05_membership-plans.md)

### Module 7 — 대시보드

- **참고**: TECH_SPEC.md 5.3절(대시보드 집계), PRD.md 6절(대시보드 화면)

- **참고**: TECH_SPEC.md 8.1~8.9절 전체
- **산출물**: Supabase 대시보드 설정 변경(이메일 확인, SMTP, 비밀번호 정책, CAPTCHA), 코드 레벨 rate limit 적용
- **테스트 방법**: 8.9절 체크리스트 표의 각 행을 실제로 확인하며 완료 표시. 특히 가입 → 확인 메일 수신 → 링크 클릭, 유출된 비밀번호로 가입 시도 시 차단되는지, CAPTCHA 없이 API 직접 호출 시 막히는지를 직접 테스트한다.
- **주의**: 일부 항목(도메인/HTTPS, Site URL)은 커스텀 도메인이 정해진 이후(Module 9와 맞물림)에만 최종 확정 가능하므로, 이 모듈에서는 우선 배포 도메인(Vercel 기본 도메인) 기준으로 설정하고 Module 9에서 재확인한다.
- **⚠️ Module 3에서 이월된 필수 항목**: Supabase 내장 메일은 시간당 발송 한도(2~3통) 때문에 가입이 실패·롤백된다. **커스텀 SMTP를 붙인 직후, "가입 → 확인 메일 수신 → 링크 클릭 → 로그인"의 해피패스를 실제 메일로 반드시 1회 검증할 것.** 이 검증 전에는 실사용자 오픈 금지. (자세한 내용: [HANDOFF_03](./handoff/HANDOFF_03_auth-screens.md))

### Module 9 — 배포 마무리 & 운영 준비

- **목표**: 커스텀 도메인 연결, 백업/모니터링 체계, 개인정보 보관·파기 정책을 확정하고 전체 플로우를 최종 점검한다.
- **참고**: TECH_SPEC.md 8.6절(도메인), 8.7절(운영 기본기)
- **산출물**: 커스텀 도메인 연결, 운영 문서(백업 주기, 모니터링 방법, 개인정보 정책) 갱신
- **테스트 방법**: 실제 운영 도메인으로 접속해 회원가입 → 로그인 → 회원 등록 → 회원권 등록 → 출석 체크 → 대시보드 확인까지 전체 플로우를 처음부터 끝까지 1회 통과시킨다.
- **다음 단계**: 이 모듈까지 끝나면 모든 개별 모듈 구현이 완료된 것이다. 실제 오픈 전 마지막 관문으로 **[FINAL_QA_CHECKLIST.md](./FINAL_QA_CHECKLIST.md)** 를 별도 세션(들)에서 수행한다. 이 체크리스트는 개별 모듈이 아니라 통합된 시스템 전체를 정상 시나리오/비정상 입력 대응/보안 세 관점에서 최종 점검하는 문서다.
