## 0. 이 문서의 목적

[TASK_BREAKDOWN.md](./TASK_BREAKDOWN.md)의 각 모듈은 **그 기능 하나가 제대로 도는지**를 검증한다. 이 문서는 모듈들이 전부 합쳐진 **완성된 시스템 전체**를 대상으로, 세 가지 관점에서 마지막으로 점검한다.

1. **정상 동작**: 실제 사용자가 의도한 방식으로 처음부터 끝까지 사용했을 때 오작동 없이 잘 돌아가는가.
2. **비정상 입력/접근 대응**: 사용자가 의도한 방식대로 하지 않았을 때 (잘못된 값 입력, 없는 데이터 조회, 인증 없이 접근 등) 앱이 깨지거나 이상 동작하지 않고 안전하게 처리하는가.
3. **보안**: 기능은 MVP 수준이어도 보안은 타협하지 않는다. 설정을 "켰는지"뿐 아니라, 실제로 뚫어보려는 시도를 해서 막히는지 확인한다.

이 체크리스트는 한 세션에서 몰아서 처리하기보다, 위 세 영역(1/2/3) 자체를 각각 별도 세션으로 나눠 진행하는 것을 권장한다 (TASK_BREAKDOWN.md 1절의 모듈 분리 원칙과 동일한 이유).

## 1. 정상 시나리오 점검 (End-to-End Happy Path)

PRD.md 5절의 사용자 스토리를 실제로 처음부터 끝까지 순서대로 수행하며 확인한다. 목업이 아닌 **실제 배포 환경(또는 배포와 동일한 스테이징)** 기준으로 진행한다.

| # | 시나리오 | 확인 내용 |
|---|---|---|
| 1 | 직원 가입 → 로그인 | 가입 후 확인 메일 수신 → 링크 클릭 → 로그인 성공 |
| 2 | 신규 회원 등록 | 이름/연락처/생년월일/성별/메모 입력 후 저장 → 목록에 즉시 반영 |
| 3 | 회원 검색 | 이름 일부, 연락처 일부로 각각 검색해 정확히 필터링되는지 |
| 4 | 회원 정보 수정 | 수정 후 상세/목록에 반영되는지 |
| 5 | 회원권 등록 (기간제) | 시작일/종료일 입력 → 상태가 "정상"으로 표시 |
| 6 | 회원권 등록 (횟수제) | 총 횟수 입력 → 잔여 횟수 = 총 횟수로 초기화 |
| 7 | 출석 체크 (기간제 회원) | 체크인 성공, 출석 이력에 기록됨 |
| 8 | 출석 체크 (횟수제 회원) | 체크인 성공 시 잔여 횟수 1 감소 |
| 9 | 회원권 갱신 | 만료 임박/만료 회원의 회원권을 갱신하면 상태가 "정상"으로 복귀 |
| 10 | 회원별 출석 이력 조회 | 해당 회원의 과거 출석 기록이 날짜순으로 보이는지 |
| 11 | 대시보드 확인 | 오늘 출석 수, 만료임박/만료 리스트 숫자가 실제 데이터와 일치 |
| 12 | 로그아웃 → 재로그인 | 정상적으로 로그아웃되고, 재로그인 시 데이터가 그대로 유지되는지 |
| 13 | 여러 직원 동시 사용 | 직원 계정 2개로 각각 로그인해 같은 회원 데이터를 함께 관리할 수 있는지 (동일 데이터 공유 확인) |

## 2. 비정상 입력 · 접근 대응 점검 (Negative & Edge Case Testing)

### 2.1 인증 관련

| # | 테스트 케이스 | 기대 동작 |
|---|---|---|
| 1 | 존재하지 않는 이메일로 로그인 시도 | "이메일 또는 비밀번호가 올바르지 않습니다" 등 일반화된 오류 (계정 존재 여부를 알려주지 않음) |
| 2 | 존재하는 이메일 + 틀린 비밀번호 | 위와 동일한 일반화된 오류 메시지 (어떤 값이 틀렸는지 구분해서 알려주지 않음) |
| 3 | 비밀번호 입력 없이 로그인 시도 | 클라이언트/서버 양쪽에서 검증되어 요청 자체가 막히거나 명확한 오류 표시 |
| 4 | 이메일 형식이 아닌 값으로 가입 시도 | 가입 폼에서 형식 오류로 즉시 차단 |
| 5 | 이미 가입된 이메일로 재가입 시도 | 중복 가입 불가 안내 (단, 존재 여부를 과하게 노출하지 않는 문구 사용 고려) |
| 6 | **로그인하지 않은 상태에서 즐겨찾기/직접 URL로 보호된 페이지 접근** (`/members`, `/attendance` 등) | 로그인 페이지로 리다이렉트, 원본 페이지 내용이 잠깐이라도 노출되지 않음 |
| 7 | 로그인 세션 만료 후 페이지 요청 | 자동으로 로그인 페이지로 이동, 오류 화면(500 등) 노출되지 않음 |
| 8 | 로그아웃 직후 브라우저 "뒤로가기"로 이전 페이지 접근 | 캐시된 데이터가 보이지 않고 로그인 페이지로 리다이렉트되거나 재인증 요구 |

### 2.2 폼 입력 관련

| # | 테스트 케이스 | 기대 동작 |
|---|---|---|
| 1 | 필수값(이름 등) 없이 회원 등록 시도 | 저장 차단 + 어떤 값이 빠졌는지 안내 |
| 2 | 연락처에 문자/특수문자 등 잘못된 형식 입력 | 형식 검증 후 오류 안내 (혹은 정책상 허용 범위 명확화) |
| 3 | 매우 긴 문자열(수천 자) 입력 | 서버 에러 없이 길이 제한 안내 또는 정상 저장·표시 |
| 4 | 이름/메모 필드에 `<script>alert(1)</script>` 같은 HTML/스크립트 입력 | 화면에 문자 그대로 표시되고 스크립트가 실행되지 않음 (XSS 방지, 2.3절과 연결) |
| 5 | 동일 연락처로 회원 중복 등록 시도 | 정책에 따라 차단 또는 경고 (의도적으로 허용한다면 그 이유가 문서화되어 있는지) |
| 6 | 회원권 등록 시 종료일을 시작일보다 이전으로 입력 | 저장 차단 + 안내 |
| 7 | 회원권 등록 시 총 횟수를 0 또는 음수로 입력 | 저장 차단 + 안내 |

### 2.3 존재하지 않는 리소스 · 권한 없는 접근

| # | 테스트 케이스 | 기대 동작 |
|---|---|---|
| 1 | 존재하지 않는 회원 ID로 상세 페이지 접근 (`/members/존재하지-않는-id`) | 404 또는 "회원을 찾을 수 없습니다" 안내, 서버 에러 화면 노출 안 됨 |
| 2 | 존재하지 않는 회원권/출석 ID 조회 | 위와 동일 |
| 3 | URL의 id 값을 다른 값으로 임의 변경해 접근 | RLS로 인해 접근 불가 또는 정상적인 "찾을 수 없음" 처리 (내부 에러 스택 노출 금지) |

### 2.4 비즈니스 로직 예외

| # | 테스트 케이스 | 기대 동작 |
|---|---|---|
| 1 | 만료된 회원권을 가진 회원 출석 체크 시도 | 체크인 차단 또는 명확한 경고 후 담당자 판단에 맡김 (정책 확정 필요) |
| 2 | 잔여 횟수 0인 회원 출석 체크 시도 | 위와 동일 |
| 3 | 회원권이 아예 없는 회원 출석 체크 시도 | 안내 메시지와 함께 체크인 처리 방식 확정 (허용/차단 정책 문서화) |
| 4 | 같은 회원을 하루에 두 번 체크인 시도 | 두 번째 시도 시 경고 및 중복 방지 |
| 5 | 체크인 버튼을 빠르게 여러 번 연속 클릭 (동시 요청) | 잔여 횟수가 한 번만 차감됨 (원자적 처리 확인, race condition 방지) |

### 2.5 시스템/네트워크 오류 대응

| # | 테스트 케이스 | 기대 동작 |
|---|---|---|
| 1 | 네트워크 끊긴 상태에서 저장 시도 | 사용자에게 재시도 가능한 오류 메시지, 데이터 유실/중복 저장 없음 |
| 2 | 서버(Supabase) 응답 지연/오류 상황 | 로딩 상태 표시, 무한 로딩이나 빈 화면으로 방치되지 않음 |
| 3 | 강제로 500 에러를 유발했을 때 | 스택 트레이스, 내부 파일 경로 등 민감 정보가 화면에 노출되지 않음 |

## 3. 보안 최종 점검 (Security Final Review)

> TECH_SPEC.md 8절(운영 전 보안 체크리스트)이 "설정을 켰는가"를 확인하는 것이라면, 이 섹션은 **실제로 우회를 시도해서 막히는지** 확인하는 것이다. 기능은 MVP여도 이 섹션만큼은 항목을 건너뛰지 않는다.

### 3.1 인증 / 세션 보안

| # | 점검 항목 | 확인 방법 | 기준 |
|---|---|---|---|
| 1 | 세션 쿠키 속성 | 브라우저 개발자도구 → Application → Cookies 확인 | `HttpOnly`, `Secure`, 적절한 `SameSite` 설정 |
| 2 | 로그아웃 시 세션 무효화 | 로그아웃 후 이전에 저장해둔 토큰/쿠키로 API 재요청 | 거부됨 (재사용 불가) |
| 3 | 이메일 미확인 계정 로그인 차단 | 확인 메일 클릭 전 상태에서 로그인 시도 | 차단되고 안내 메시지 표시 |
| 4 | 비밀번호 정책 강제 | 7자 이하, 단순 숫자만 등으로 가입 시도 | 거부됨 |
| 5 | 유출 비밀번호 차단 | 알려진 유출 비밀번호(예: `password123`)로 가입 시도 | 거부됨 |
| 6 | 로그인 실패 반복 시 제한 | 동일 계정으로 여러 번 틀린 비밀번호 입력 | 일정 횟수 이후 지연/차단 발생 |

### 3.2 인가 / 접근 제어 (RLS)

| # | 점검 항목 | 확인 방법 | 기준 |
|---|---|---|---|
| 1 | 비로그인 상태 직접 API 호출 | 브라우저 콘솔에서 `anon` key로 Supabase REST API(`/rest/v1/members` 등)를 로그인 없이 직접 `fetch` 호출 | 빈 배열 또는 권한 오류, 실제 데이터 반환되지 않음 |
| 2 | 로그인 상태에서 타 데이터 접근 시도 | 존재하는 다른 레코드의 id를 알아내 직접 조회/수정 요청 | RLS 정책 범위 내에서만 허용되는지 확인 (직원 간 데이터 공유 정책과 일치하는지) |
| 3 | Security Advisor 재실행 | Supabase 대시보드 Database → Advisors | 경고 0건 |
| 4 | SECURITY DEFINER 함수 점검 | 함수 목록 전수 확인 | 꼭 필요한 함수만 존재, 내부에 호출자 권한 재확인 로직 포함 |

### 3.3 비밀 정보 노출 점검

| # | 점검 항목 | 확인 방법 | 기준 |
|---|---|---|---|
| 1 | 클라이언트 번들 내 비밀키 검색 | 배포된 사이트의 페이지 소스/JS 번들에서 `service_role`, DB 비밀번호 등 문자열 검색 | 검출되지 않음 |
| 2 | GitHub 커밋 이력 전수 검사 | `git log -p` 전체 검색 또는 gitleaks/trufflehog 같은 시크릿 스캐너 실행 | 비밀값 커밋 이력 없음 |
| 3 | `.env` 커밋 여부 | 저장소에서 `.env`, `.env.local` 파일 존재 여부 확인 | 커밋된 적 없음 (`.gitignore`에 포함) |
| 4 | 노출 이력이 있다면 재발급 여부 | Supabase 대시보드 API 키 발급일 확인 | 노출 이력이 있었다면 재발급 완료 상태 |

### 3.4 입력값 검증 / XSS / Injection

| # | 점검 항목 | 확인 방법 | 기준 |
|---|---|---|---|
| 1 | XSS 방어 | 회원 이름/메모에 `<script>`, `<img onerror=...>` 등 입력 후 화면 렌더링 확인 | 스크립트 실행 없이 텍스트로만 표시 |
| 2 | SQL Injection 방어 | 검색어에 `' OR '1'='1` 등 입력 | 정상 텍스트 검색으로 처리되고 전체 데이터가 노출되지 않음 (Supabase 클라이언트 사용 시 기본 방어되나 직접 작성한 RPC/SQL이 있다면 별도 확인) |

### 3.5 전송 구간 / 도메인 설정

| # | 점검 항목 | 확인 방법 | 기준 |
|---|---|---|---|
| 1 | HTTPS 강제 | HTTP로 접속 시도 | HTTPS로 자동 리다이렉트 |
| 2 | 인증서 유효성 | 브라우저 주소창 자물쇠 아이콘 확인 | 유효한 인증서 |
| 3 | Site URL / Redirect URL 일치 | Supabase Auth → URL Configuration | 운영 도메인과 정확히 일치, `localhost` 등 개발용 값 제거 |
